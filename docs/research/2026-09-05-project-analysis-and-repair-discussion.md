# 项目现状与下一轮修复讨论

日期：2026-09-05。范围：当前工作区的项目结构、功能入口、近期修复记录、基础验证与维护债务。用户已明确本轮重点为战斗运行效率、Terrias 精灵系统设计、角色与卡牌功能、代码结构；性能症状是整场持续卡顿或越打越慢。本文用于讨论修复范围，不将历史修复记录中的测试结果作为本轮执行结果。

本轮判断：正式产品、共享运行时和验证入口已经有明确归属，基础检查通过。接下来的修复应围绕具体使用流程建立问题清单，优先处理用户实际遇到的故障，再收口近期修改的实机验收与相关维护债务。

**四个重点的分析与讨论提案**

| 重点 | 已核对的现状 | 建议先解决的问题 |
| --- | --- | --- |
| 战斗效率 | 已有共享帧调度、资源/表索引缓存、卡牌脏字段合并、直接 C# 初始化委托和性能计数；精灵读模型按代次缓存。最近录制优化的微基准不覆盖 Unity、GC 和整场帧耗时 | 建立同一配置下战斗早期/中期/后期的帧耗时、分配、对象、订阅及队列基线，定位随时间增长的工作；先证明瓶颈，再决定优化边界 |
| 精灵设计 | 永久收藏、旅程六槽编队与战斗实体已分开；战斗只冻结一个出战 UID。等级、资质、四本源、归元、元素、意图/被动装配及五槽圣遗物同时存在 | 明确精灵是角色卡组的战术伙伴，还是独立长期养成主轴；再决定六槽的战斗价值、养成层数及属性预算 |
| 角色与卡牌 | 乌娜的灼烧/余烬/日耀、洛奈尔的星石/奇迹/星谱、哥伦比娅的获牌减冷却/水元素与月反应有不同核心循环 | 为每个角色建立“文字描述—触发时点—实际效果—重复触发限制—清理与归属”清单，连同精灵、多段伤害、生成牌及百变一起验证 |
| 代码结构 | 分层和处理器注册已经存在，但精灵召唤仍直接承担网络、实体创建、快照和返卡；架构例外清单也登记了这些反向依赖 | 先收口本轮功能涉及的责任边界；Application 编排一次用例，Mechanics 决定规则，GameApi 访问宿主，Network/UI 作为适配器 |

战斗效率的首轮测量建议使用同角色、同类敌人、相同模块配置，比较待机、常规出牌、连续生成牌、多段元素结算和战斗结束后的空闲状态。记录帧耗时分布（含较慢的 95%/99% 分位）、GC 分配与停顿、卡牌视图/特效数量、订阅数量、待处理队列，以及状态刷新/录制/日志耗时。跨下一场再测一次，以区分单场历史增长和跨场残留。暂未设定性能达标数值，需先确认实际硬件、目标帧率与可复现负载。

用于归因的模块开关对照只是一种诊断手段，最终仍需在用户需要的功能组合下验收。网络负载应区分单机与联机：[精灵运行态广播](../../Terrias-Dev/Mechanics/SpiritSummonService.cs)已经在构造广播快照前检查多人会话，不能把它直接归因为单机常驻卡顿。

精灵系统有三个具体设计取舍，均不是已确认的代码 Bug：

- **六槽携带与一只出战**：[战斗部署服务](../../Terrias-Dev/Mechanics/SpiritBattleDeploymentService.cs)冻结唯一 `active`；撤回后可再次召唤，但不能在同场换为另外五只。需要决定其余槽主要承担后续战斗备选/经验培养，还是希望形成同场替换策略。
- **捕获与首次全量发放**：[发布配置](../../Terrias/Configuration.json)默认开启首次发放全部 58 个 Profile 个体；捕获仍用于重复个体、资质与归元等。需要明确全量发放属于正式体验还是测试便利，再评估捕获的激励。
- **成长深度与卡组地位**：[精灵规则](../Terrias/modules/08-精灵球捕获与精灵召唤.md)和[圣遗物规格](../Terrias/design/11-精灵圣遗物系统实现规格.md)同时提供多种永久成长渠道。建议先确定“种族带来什么独特战术、养成允许多大数值提升、角色出牌如何影响精灵”，再调整具体层数和数值，避免只增加培养操作。

代码结构的优先候选是 [SpiritSummonService](../../Terrias-Dev/Mechanics/SpiritSummonService.cs)、[SpiritCollectionApi](../../Terrias-Dev/GameApi/SpiritCollectionApi.cs)与[精灵管理界面](../../Terrias-Dev/Hooks/Ui/SpiritManagementPanel.cs)。选择理由是它们处于本轮设计变动的边界，并非文件长就必须拆分。已有 [SpiritReadModelStore](../../Terrias-Dev/Mechanics/SpiritReadModelStore.cs)和[圣遗物应用服务](../../Terrias-Dev/Application/SpiritArtifactApplicationService.cs)可作为复用现有职责的起点。

**建议的讨论顺序**

1. 性能先建立可复现的整场基线，并按用户已反馈的持续卡顿/随时间变慢定位根因；与此同时讨论精灵的玩法定位。
2. 精灵设计先确定战斗控制、六槽价值、成长深度和卡组配合，再决定规则与存档迁移。
3. 角色与卡牌按核心循环逐项核对，优先覆盖连续获牌、状态连锁、多段元素反应和精灵参与；具体角色/卡牌故障仍待用户补充。
4. 代码结构随选定功能一起收口，保留必要数据兼容，并更新相应文档。工具箱旧配置、AI 新架构和无关模式改造暂列后续候选。回放在本轮主要作为战斗负载来源及共享生命周期消费者检查，不自动取代用户指定的四个重点。

每个选定问题用一条记录追踪：现象与证据 → 根因和责任边界 → 目标行为 → 涉及代码/数据/配置/资源 → 自动验证 → 实机验收 → 发布状态。测试通过、包发布和实机验收分别记录。
