# 训练与游戏主体验证分离

## 管线边界

自动战斗 AI 现在使用两条职责明确的管线：

1. 外部训练与模拟校准在独立 `.NET 8` Worker 中运行。它负责大规模课程训练、分层回放、同种子底模对照和普通/高级难度统计。
2. 游戏主体验证在 Witch 进程中运行。它只负责确认候选模型能够在真实 `FightManager`、`RoleTable`、`FightUI` 交互入口和本体卡牌脚本上完成关键战斗。

外部模拟结果不能替代游戏主体回执，游戏主体回执也不回流训练集。这样可以防止验证数据污染训练，同时把耗时的大样本工作留在可并行的外部进程。

## 外部训练控制台

`AuraFoundationTrainer.ControlCenter.exe` 是独立的 `.NET 8` WPF 调度器。它和 Worker 一同发布到 `AuraToolsExp/TrainingWorker/`，可从设置页“外部训练控制台”启动，也可在游戏关闭时直接运行。

控制台默认以自身 EXE 所在的 `TrainingWorker/` 为锚点，自动定位上一级 `AuraToolsExp/` 和同级运行环境的 `ModsData/`。仓库或游戏目录整体移动后不需要修改本机绝对路径；`--mod-root` 与 `--data-root` 仅保留为诊断时的显式覆盖参数。

控制台负责：

- 编辑基础参数和高级参数，并在启动前显示估算战役数；
- 从冻结 campaign、ruleset 和原生程序包生成 schema 8 任务；
- 启动或重新连接 Worker，轮询阶段、进度、吞吐、剩余时间和诊断；
- 通过取消文件请求安全取消，保留满足协议的恢复点；
- 从已接纳 Champion，或带完整检查点的 `training-rejected-resumable` 工作模型发起下一轮谱系训练；
- 在控制台关闭后让 Worker 继续运行，稍后可重新连接；
- 任务结束时自动切换到“运行监控”，通过完成弹窗、提示音和任务栏闪烁明确反馈结果；
- 在“训练配置”页持续保留最近任务的验收状态、胜场和恢复点摘要。

同一个成功案例库只允许一个训练 Worker 持有写租约。游戏内训练和外部控制台都会检查该租约，避免并发修改案例库。控制台中的“迭代数”表示单次任务内部迭代；继续训练时，正式 Champion 与尚未过门禁但可恢复的 `WorkingChampion` 分开保存。后者可以继续学习，却不会被包装或展示成已验收底模。

续训兼容指纹冻结角色/使魔/卡包主体、规则与原生程序、网络和特征协议、学习策略及验收语义，但不冻结本轮迭代预算和新请求种子。有效恢复始终沿用检查点中的原始运行种子、难度分区和模型种子，保证一条训练谱系不会因点击“继续”而悄悄换题；只有检查点不兼容时才使用新请求的种子从头开始。

## 工件与门禁

游戏主体验证请求和回执遵循 `CombatGameValidationProtocol`。回执同时绑定：

- 决策风格与模型 ID；
- 模型包 SHA-256；
- Witch 游戏程序集版本；
- 固定世界推演包 ID 与版本；
- 冻结规则集哈希；
- 当前权威预编译程序包哈希。

其中任一项变化，旧回执立即失效。候选晋升需要依次通过：

1. 模型自身的分组验证；
2. 外部同种子底模对照评估；
3. 规则基线能力探针增益门禁；
4. 游戏主体最终首领验证回执。

能力探针门禁默认启用。Champion 在 Normal 和 Advanced 任一难度都不能低于
规则基线，并且总胜场至少增加 1 场或平均完成深度至少增加 0.5。未达到时
Worker 跳过 200/500 场正式隔离验证，结果保持可恢复，不会用“与基线持平”
冒充模型能力提升。

控制台设置 schema 3 会将旧版控制台因复选框加载缺陷而错误保存为关闭的
能力探针门禁恢复为默认开启；迁移完成后，用户在新版界面中的显式选择会正常持久化。

Worker 只在 `training-accepted` 时生成 `foundation-model-package-v2.json`。包内绑定模型文件及哈希、训练请求、规则集、campaign、原生程序包、游戏参数指纹和 Worker 哈希；导入时任一文件缺失、哈希错误、角色/使魔/卡包/牌组倾向不兼容或训练结果未接纳都会被拒绝。

设置页“选择底模验证”只把外部包复制到隔离的待验证区，并写入 `evaluationModelId`。它不会替换当前实战模型，也不会自动加入模型库。待验证模型必须依次通过：

1. 普通正式世界推演；
2. 高级正式世界推演；
3. 游戏主体验证；
4. 用户点击“加入模型库”。

最后一步默认仍保持模型关闭。选择模型库中的已有模型会清除待验证目标，避免后续推演误用旧的外部候选。

## 随 MOD 发布的内置底模

AuraToolsExp 启动时会在后台扫描 `AuraToolsExp/ModResource/Model/*.json`。扫描只处理该目录顶层，按文件名稳定排序；每个文件独立执行 64MB 上限、严格 UTF-8、底模包协议和正式隔离验收校验。单个损坏文件只会记录失败，不会阻止其他内置底模注册。设置页“底模导入”区域提供扫描结果和“重新扫描内置底模”，便于开发期热测。

内置底模包必须额外声明独立的 `ModelVersion`，例如 `1.0.0`。它表示发布版本，不复用包格式版本、网络协议版本或训练 Epoch。模型库显示名由包内稳定 ID 和随 MOD 发布的游戏主体目录解析为：

`角色名称-使魔名称-卡包数量卡包-v底模版本`

例如：`阿米莉娅-报丧偈羽-18卡包-v1.0.0`。模型库中的物理文件继续使用 `model-<hash>.json`，中文名称只作为可编辑显示名。

注册遵循非破坏性规则：同一模型 ID 与同一源包 SHA-256 直接去重；同一模型 ID 但不同哈希拒绝覆盖；同一角色、使魔、卡池和版本对应不同模型 ID 时要求提升 `ModelVersion`；不同版本可并存。自动注册不会选择或启用模型，不会删除已入库但本次未随 MOD 提供的模型，也不会覆盖用户手动修改过的显示名。模型库位于 `ModsData/AuraShared/Data/Owners/AuraToolsExp/FoundationModels/`。

## 是否需要可见 UI

不需要把大规模训练或大部分验证做成可见游玩。

游戏主体验证仍保留真实 `FightUI` 对象和交互执行路径，因为自动战斗的合法动作最终通过这些入口提交；默认只使用 `CanvasGroup` 隐藏画面并关闭射线，不禁用 UI 逻辑。这样比真正的无 UI 游戏进程更接近玩家运行时，又省去渲染和人工等待。

建议发布前只补一轮很小的可见冒烟测试，用于检查画面层、按钮层和动画层没有妨碍真实交互。它不是训练步骤，也不需要覆盖大量种子。

## 默认实机用例

每个待晋升模型默认各运行一次：

- 永夜；
- 魔王；
- 神圣审判机关；
- 勇者卡洛琳。

每场设置动作数和时间上限。角色状态在验证前序列化，并在每场结束、取消或失败后还原；验证使用 `IsFake` 战斗，避免把奖励和进度当作正式游玩结果。

默认晋升门禁要求每场至少完成一个真实动作、没有无效运行，并完整覆盖四个用例。胜负会写入回执，但默认不设最低胜场，因为实机验证沿用当前角色构筑，少量胜负不能和外部固定世界种子的统计直接比较；需要固定人工构筑验收时，可在配置中提高 `minimumWinsPerFinalBoss`。

请求与回执写入 `ModsData/AuraShared/Logs/AuraToolsExp/game-validation/<模型摘要>/`。设置页的“实机验证”和“打开回执”用于启动验证与查看结果。外部包的隔离副本和清单写入 `ModsData/AuraShared/Logs/AuraToolsExp/external-foundation-validation/`；清除待验证项只移除该隔离副本，不影响训练原目录。
