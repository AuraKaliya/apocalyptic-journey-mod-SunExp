# 训练数据与模型演进

## 原则

“自主训练”不是在每次出牌时持续反向传播。当前采用可审计的批次流程：

1. 游戏内受控采样；
2. AuraToolsExp 在后台从本地样本批量生成候选；
3. 人工导入小型、只读、可校验的模型；
4. 影子模式对比；
5. 逐步启用；
6. 最后才评估受限在线适应。

执行安全、合法性和回退能力优先于模型复杂度。

## 当前样本

协议：`aura.combat-ai.sample.v4`

当前字段包括：

- 战斗会话、决策序号和根事务 id；
- 动作前后状态指纹；
- 决策配置、游戏版本和共享层版本；
- 全部候选的稳定来源 id、合法性、拒绝原因、语义、特征、效用分项与规则分数；
- 最终选择及其启发式预测分数；
- 当前威胁的可格挡、不可格挡和持续伤害；
- AI 推荐的回合方案、玩家教师动作和推荐候选差异；
- `selection.v1` 选择轨迹：执行者、实际动作、AI 预选、一致性和标签用途；
- AI 预选是否在玩家操作前可见，用于隔离可视提示的锚定效应；
- 每个候选的“实际执行”“人工选择”“AI 预选”观察标记；
- 动作结算状态、超时/接管/失败原因；
- 分项短期奖励、终局状态和战斗结果。

文件使用真正的 JSON Lines：每个样本严格占一行。旧
`auto-battle-training-v1.jsonl` 和 `auto-battle-training-v2.jsonl` 只作为
历史审计数据保留；v3 会在训练时转换为上下文特征，新样本写入
`auto-battle-training-v4.jsonl`。

当前奖励主要来自：

- 敌方生命下降；
- 玩家生命变化；
- 可格挡缺口内的有效护盾和溢出护盾惩罚；
- 能量变化。

这仍然是启动数据，不等同于整局价值。v4 已加入伤害通道、人工教师、计划、
手牌变化、结束回合成本和终局奖励，但抽牌质量、状态持续时间和折扣回报仍需
在离线训练管线中计算。

## 当前训练流程

1. 在设置中开启“记录训练样本”。
2. 选择“自动轨迹采集”“人工示范采集”或“全部轨迹采集”。
3. 人工教师模式下关闭自动接管并正常出牌；AI 只记录同状态推荐。
4. 在 AuraTools 设置中点击“生成候选”；本地 C# 训练器在后台运行。
5. 查看日志中的样本数、偏好对数和候选路径，再点击“导入候选”。
6. 选择“影子评估”，先审计底模与模型建议差异。
7. 通过回归后再选择“受限应用”。

设置界面会持续显示后台任务的排队、样本读取、训练、候选写入、候选就绪、
导入和失败状态。训练参数可以选择“稳健”“标准”“强适应”预设；展开高级
参数后可调整训练轮数、学习率、L2、最大修正、最低有效偏好对和动作类别最低
样本。修改任一高级参数后预设记为“自定义”。生成任务会复制一份不可变参数
快照，并把实际参数写入候选模型的 `TrainingParameters`。

此流程完全在游戏与 MOD 环境中运行，终端用户不需要 Python。仓库中的 Python
工具只用于开发机复核训练器结果，不是发布后的用户操作路径。

训练器只把已完成的人工/AI 分歧转换为成对偏好：

```text
人工实际动作 > 同状态 AI 预选动作
```

人工与 AI 一致的样本用于一致率和结果校准，不重复强化当前策略。自动策略样本
始终作为轨迹与回报数据进入统计报告，不转换成偏好标签；即使自动动作获得负
回报，也不能据此断言所有未执行动作都更优。历史参数 `-IncludePolicy` 仅保留
命令兼容并输出弃用提示，不再改变训练集。

人工分歧样本根据预测可见性分层：

- `PolicyVisibleToHuman=false`：隐藏预测的独立教师样本，偏好权重 2；
- `PolicyVisibleToHuman=true`：玩家看过黄/红/绿预测标记，偏好权重 0.5。

报告分别统计可见和隐藏样本数量及一致率，避免把提示导致的跟随行为误认为
独立教师判断。

每次运行训练器都会输出：

```text
auto-battle-training-report.json
```

报告包含人工/自动样本数、选择协议覆盖率、人工与 AI 一致率、AI 预选动作分布、
实际动作分布、人工覆盖方向，以及自动轨迹的即时奖励和折扣回报摘要。只生成
报告时使用：

```powershell
tools\Train-AuraCombatAi.ps1 -ReportOnly
```

## 特征版本

v4 已固定以下协议字段：

```text
modelProtocol
featureSchemaVersion
gameBuild
sharedBuild
decisionProfile
battleOutcome
```

`ownerModSetHash` 等 MOD 环境信息可以作为诊断元数据保留，但不作为模型输入、
加载门禁或启用条件。模型依据已经统一和限制过的战斗上下文迁移；未覆盖语义由
适用性门控回退到底模。

特征要求：

- 名称稳定；
- 数值有限，不允许 NaN 或 Infinity；
- 缺失值有固定默认值；
- 训练和运行时使用同一归一化参数；
- 不能使用动作之后才知道的信息；
- 不直接使用不稳定的 Unity instance id 作为可学习语义。

## 数据拆分

必须按整场战斗拆分，不按单个动作随机拆分：

- 训练集：约 70%；
- 验证集：约 15%；
- 测试集：约 15%。

同一 seed、同一场录像或重放派生的样本必须落在同一分组。还应按角色、牌组、敌人、游戏版本和 MOD 组合观察分布偏差。

## 第一模型实现

### 线性残差

优点：

- 参数量小；
- 可解释；
- 手写推理简单；
- 模型通常只有数 KB；
- 容易限制输出范围。

当前已经实现 MOD 内 C# 成对排序训练器、均值/尺度归一化、有界 C# 推理、
候选模型验证和共享配置导入。残差输出严格裁剪到 `[-2,+2]`，并乘以语义、
动作类别样本支持和特征范围三重适用性，默认关闭。

### 小型 MLP

建议起点：

- 输入为固定特征向量；
- 两个隐藏层，每层 16 到 32 个单元；
- ReLU 或 tanh；
- 单一标量残差输出；
- 输出裁剪到有限范围。

这种模型通常可控制在几十 KB，运行时可以用简单数组推理，不必引入大型神经网络运行库。

### 暂缓方案

以下方案必须有明确收益证据后再评估：

- ONNX Runtime 等大型原生依赖；
- 大型 Transformer；
- 游戏内持续训练；
- 无界 Monte Carlo 搜索；
- 每张卡独立携带模型。

它们会显著增加包体、平台兼容、加载时间和诊断成本。

## 模型文件合同

模型至少包含：

- model id；
- model protocol；
- feature schema version；
- 输入维度；
- 层结构；
- 权重数据；
- 归一化参数；
- 训练数据摘要；
- 校验和；
- 创建时间和工具版本。

建议首轮限制：

- 单模型不超过 256 KB；
- 只允许已知层类型；
- 所有权重必须为有限数值；
- 输入维度必须精确匹配；
- 校验失败立即拒绝；
- 不允许模型文件声明任意类型或执行代码。

## 评估指标

离线指标：

- 候选排序一致率；
- 与人工选择的 top-1/top-3 一致率；
- 非法动作建议率；
- 相对启发式模型的累计回报；
- 不同角色和 MOD 的最差分组表现。

游戏内影子指标：

- 模型建议与实际规则选择的差异；
- 假设采用模型建议时的短期奖励；
- 推理耗时 P50/P95/P99；
- 模型加载失败和回退次数。

最终对局指标：

- 胜率；
- 平均受伤；
- 平均回合；
- 资源浪费；
- 玩家接管率；
- 超时和异常率。

## 上线顺序

1. `capture only`：只采样。
2. `offline replay`：只离线评估。
3. `shadow`：游戏内推理但不影响动作。
4. `bounded residual`：只允许小幅修正。
5. `profile opt-in`：玩家显式选择学习模型。
6. `default candidate`：长期验证后才考虑默认启用。

任何阶段发现非法动作率、异常率或最差分组明显恶化，应立即回退到启发式模型。
