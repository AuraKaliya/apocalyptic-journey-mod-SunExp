# AuraToolsExp 统一 CG 系统契约

> 状态：当前实现合同  
> 更新日期：2026-09-06

## 1. 功能模型

CG 按触发主体分为三类，界面只公开这三个入口：

| 主体 | 信号 |
|---|---|
| 角色 CG | 美餐、使用技能、游戏主体原生濒危（`Dying`）判定 |
| 卡牌 CG | 卡牌使用 |
| 事件 CG | 胜利原因、战斗开场、战斗失败、冒险结算 |

角色 CG 的元素是参与角色，卡牌 CG 的元素是卡牌，事件 CG 的元素是一次
冒险或战斗事件。历史“美餐 CG”“技能 CG”和“伤害结算 CG”不再拥有各自的
注册、缓存、Canvas、RPC 或播放链路。

## 2. 信号注册

内容 MOD 通过 `SharedResources/cg.registry.json` schema 4 声明：

- `subjectType`、`subjectIds`：触发主体；
- `signals`：可响应的语义信号；
- `match`：技能 ID、事件标记等可选事实；
- `scene`：插画主题、角色姿势、面部构图与终局独占策略；
- `presentation`：时长、淡入淡出和显示层级。

AuraToolsExp 在统一 Hook 中把游戏行为转换为信号，再由共享查询服务选择注册项。
运行时不再用 `kind`、目标角色数组或分散的功能 Hook 猜测 CG 类型。schema 3
只允许一次性迁移到 schema 4；新清单不得继续写入旧字段。

## 3. 两阶段数据边界

本地主机可以使用较丰富的 `AuraCgSceneSource` 做判断，例如玩家身份、角色、
特殊战斗标记和已处理的结算指标。规划器必须在网络发送和实际展示前把它收敛为
`AuraCgScenePlan`：

- 实际角色 ID 的稳定顺序；
- 每个参与者的归一化面部位置/大小、缩放、层级与轻动态开关；
- 主题背景与角色层的 owner-qualified 逻辑资源 ID；
- CG、信号和表现配置 ID；
- 仅在画面确实需要时保留的处理后指标。

计划不得包含原始伤害记录、排名源数据、战斗历史、本地绝对路径、图片字节、
缓存键或可执行回调。接收端只验证计划和注册身份，并在自己的资源目录解析逻辑 ID。

队伍场景当前采用v2协议与`team-poster.v3`布局。立绘面部标注、前景和角色附属层
通过本地`AuraCgSceneArtwork`解析，不进入网络计划；旧v1场景不能按新锚点语义播放。
详见[立绘海报运行合同](team-event-cg-poster-v3-design.md)。

## 4. 队伍终局场景

胜利、战斗失败和冒险结算从当前冒险队伍独立冻结参与者快照，不依赖
DamageMeter。顺序以权威玩家队列为准，相同输入必须生成相同布局；当前布局支持
1 至 8 名角色。终局 CG 以一张队伍场景独占展示，开始时清除等待中的普通 CG，
不得为每名角色连续播放多张单人图。

战斗开场使用同一场景规划器；空范围表示全部战斗，有界迁移保留的战斗 ID 仅限制
开场场景。胜利必须携带稳定 `outcomeReason`：游戏主体至少区分普通胜利、点金手
脱离、仪式胜利和诅咒胜利。普通逃跑不属于失败，不能触发战斗失败 CG。内容 MOD
可注册新的胜利原因，但共享层只处理通用原因标识，不包含内容判断。

## 5. 单一表现与缓存

所有类型最终进入 `AuraCgPlaybackCoordinator`、`AuraCgOverlayPresenter` 和
`AuraCgUnityMediaRepository`。场景背景、角色、前景和附属层与单图 CG 共用生命周期、显存预算、
预载、租约和释放规则。界面只创建一个共享 Overlay Canvas；功能模块不得自行创建
Canvas、静态 Sprite 字典或播放器。

缓存键必须包含 owner、资源逻辑 ID 和会改变解析结果的角色/配置身份。替换配置后
不得命中旧图，不同角色也不得错误共享角色层。未进入缓存的临时 Sprite 必须立即释放。

## 6. 网络与权限

共享 CG 网络协议只传处理后的请求或场景计划，负载上限为 16 KiB。主机负责解析
富上下文、选择注册项和生成队伍布局；客机不重算规则。接收端校验发送者所有权、
协议版本、主体/信号/CG 注册关系、数量和数值范围。战斗外的美餐与冒险结算仍绑定
已认证玩家身份，不能用任意角色 ID 冒充 owner。

不兼容、资源缺失或验证失败只降级当前 CG，不得阻断战斗、结算或大厅通信。

## 7. 配置与迁移

角色 CG 页面使用顶部角色选择器和技能/美餐/低生命标签，只实例化当前上下文的资源
行；卡牌 CG 页面管理注册卡牌。事件 CG 页面使用胜利/战斗开场/战斗失败/冒险结算
标签，配置与预览互斥显示，每个场景独立保存启用、自定义背景、逻辑画布、时长和轻动态。
背景为空时使用对应主题插画，角色按事件姿势、当前皮肤立绘、同角色中性立绘的规则选择。
设置页嵌入预览与全屏播放复用同一个海报渲染器和资源解析链路，支持切换预览队伍。
角色姓名来自接收端本地资源元数据，用作队伍署名，不进入场景计划或RPC。
本地关闭轻动态时，接收远端场景也不启用镜头、图层位移或光效脉动。
注册默认、AuraToolsExp 默认和玩家覆盖必须分层保存，恢复默认就是删除本地覆盖。
技能与低生命资源的当前选择按“角色 + CG 类型 + 技能上下文”保存到
`roleSelections`；版本以 [AuraToolsSkillCgSettings.CurrentSchemaVersion](../../AuraToolsExp-Dev/Config/AuraToolsSkillCgSettings.cs)
为准，资源级 `roleEntries` 只保存表现覆盖。美餐标签当前仍通过 Feast 的
`ResourceOverrides` 与 `SaveRoleSettings` 保存选择，诊断时须区分这条配置路径；
它不建立独立的共享播放器或 RPC。运行时在发出角色信号前写入
唯一 `resolvedCgId`，避免多个默认启用资源同时排队，也避免通配资源在一个技能中的
选择误伤同角色的其它技能。

旧配置只作为有界迁移输入：历史伤害结算背景/时长迁入每个事件场景，历史特殊战斗
ID 只迁入战斗开场范围；复制进 `roles[].rules` 的注册项迁为 owner-qualified 上下文选择，
真正的人工规则迁为 AuraToolsExp 拥有的本地 CG 注册项。UI 不显示或编辑注册源路径。

迁移完成后，运行时权威来源是 schema 4 注册表、统一 CG 配置和共享展示服务。旧的
伤害结算 RPC、Payload、AssetCache、Canvas 和播放器必须不存在，事件 CG 也不能反向
引用 DamageMeter。

## 8. 验证门禁

发布前至少验证：

1. schema 3 到 schema 4 的有界迁移及 schema 4 严格读取；
2. 三类主体和全部信号的匹配、优先级与去重；
3. 1 至 8 人布局、稳定角色顺序和终局独占播放；
4. 处理后网络计划不泄漏路径、缓存键或原始伤害数据；
5. owner-qualified 资源在每个客户端本地解析；
6. 低生命只消费游戏主体 `StatusManager.PlayVocal(Dying)` 判定，每场战斗首次进入时触发，
   新战斗重置；配置中不存在玩家阈值；
7. 点金手、仪式、诅咒、普通胜利、普通逃跑和失败的原因分类；
8. 922×838 与 1280×720 下角色/类型和事件/预览页面只有一个滚动区且无溢出；
9. 旧角色规则编辑器、注册默认复制器、伤害结算运行时和私有表现链路均已移除。
