# 奥莉米娅角色与织梦黄金体系

> 确认规格：2026-09-06。宿主结算依据为与仓库 Managed 指纹匹配的 `1.0.24831968`。
> 自动化检查覆盖生产代码和声明；Unity 实机与双机验收另列。

## 1. 角色与能力

- 角色：奥莉米娅 / Olimya，称号【黄金的魔女】。
- 完整角色 ID：`Terrias_olimya_olimya`。
- 基础最大生命值：80；其他开局参数沿用主体规则。
- 一个主动、两个被动。未建立专属命座，使用现有通用旅人座。

**织梦的魔女**：每段伤害结算后，获得等同该段实际损失生命值的护盾。自己的回合开始时，先清空全部旧护盾，再处理其他回合开始效果。

护盾承伤不生成新盾；普通伤害与无视护盾的伤害均按实际损血计算。直接支付或设置生命值不是伤害。伤害先发生，护盾后生成，不能抵挡触发它的那一击。原生首死救援把伤害转换成治疗时不触发该被动。

**黄金的魔女**：每获得2点真实金币，额外制造1金币；每消耗2点真实金币，额外制造1金币。收入与支出分别累计不足2点的零头。

被动跟随当前有效角色：奥莉米娅与百变化身为她时生效，离开该身份后停止，期间收支不追溯计算。战斗外也生效。制造的金币不再触发制造，不再次乘金币获取倍率。初始余额、读档恢复和伪金不计入；已经制造的金币正常保留。

**点金**：0费，冷却3回合，开战时可用。选定一名敌人（包含首领）施加【黄金化】，持续至施法者下次回合开始。当前角色不是奥莉米娅时不能使用。

**黄金化**：负面状态，上限1层。每段伤害令攻击者获得等同目标实际生命损失与护盾消耗之和的金币，不计过量击杀、免疫或0伤害。重复施加刷新期限，不叠加倍率。金币归实际攻击者；精灵、投影通过已有语义所有权归属到拥有者。没有玩家钱包的伤害来源不能为施法者凭空创造收益。

## 2. 伤害与回合结算

`OlimyaRuntime` 使用原生 `CustomDamageType.ApplyDamage` 前后入口建立逐段伤害上下文，再在该调用内部的 `CustomDamageType.ShowDamage` 读取原生最终结算数值。快照包含伤前生命、护盾、伤害类型是否无视护盾、攻击来源、收款者与当时的黄金化状态。

普通伤害的护盾消耗为最终伤害与伤前护盾的较小值；实际损血为余下伤害与伤前生命的较小值。这样既尊重原生减伤、生命损失限制，也排除过量伤害。伤前已经倒下的角色按0可损失生命计算，避免首死救援完成时误发护盾。

伤害栈覆盖嵌套反伤等情况。对应帧只结算一次；脱离实际伤害调用的网络 `DamageText` 展示不发放奖励。护盾仅由当前玩家自身的奥莉米娅被动发放。

回合清盾发生在 `PlayerTurnEntering`，早于主体 `StartRound` 事件。`FightUI.IsReset` 的界面重进分支不会重复清盾或推进冷却。主动冷却只在奥莉米娅身份有效时推进；百变的其他冻结与恢复规则沿用现有职业技能系统。

## 3. 钱包与角色所有权

`OlimyaEconomyService` 观察当前玩家 `RoleTable.set_Money` 及其原生 `Money` 属性通知，不仅观察战斗脚本，因此奖励、商店、卡牌等常规钱包收支均可触发。

普通收入先经过主体金币倍率。额外制造在原生属性通知前写入已经核对的 `RoleTable.money` 字段，让原通知发布最终余额，不再次调用收入 setter，不重复通知，也不临时修改全局金币倍率。嵌套的正常钱包交易分别结算。

收入、支出余数分别保存于当前冒险角色 `SpecialVarMap` 的 `TerriasOlimyaIncomeRemainder`、`TerriasOlimyaSpendingRemainder`，值只能为0或1。角色初始化期间禁止制造；加载与状态恢复没有新的钱包交易，不回算余额。仅当前 `RoleTable.Instance` 可接受本地被动。制造仍受主体钱包上限约束。

## 4. 黄金化与多人流程

黄金化使用 `RpcOlimyaGoldenization` 请求主机执行，应用层负责玩法验证。协议包含版本、战斗代次、单调序号、命令 token、施法者状态 ID 与目标状态 ID；发送者由现有服务器入口绑定，不能从载荷声明身份。

- 仅接受当前已开始战斗的请求，拒绝初始化窗口、旧战斗、重复／倒序与非拥有者请求。
- 施加时验证奥莉米娅有效身份、施法者存活和目标为存活敌人。
- 主机只保留目标当前的施法者。刷新来自另一名奥莉米娅时，原施法者下回合不能清除新标记。
- 原生 Buff 通道同步实际黄金化状态；到期通过主机移除。
- 施法者自己的下一回合发出到期请求，即使此时已经变成其他角色也会执行。
- 战斗重开、重新初始化和结束时清理标记及待到期状态。

伤害在目标的原生执行端结算。产金通过具有有效来源 ID 的新执行器调用原生 `ChangeMoney`，送到攻击者所属玩家；精灵与投影先解析其语义拥有者。钱包接收端沿用主体玩家类型与所有权路由，随后按收款者当前职业决定是否制造额外金币。
