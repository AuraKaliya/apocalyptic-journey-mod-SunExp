# 精灵收集、培养与出战系统

> 状态：当前实现合同
> 更新日期：2026-08-27
> 当前版本：收藏档案 9、养成注册表 schema 2、意图注册表 schema 3、Partner 协议 21

## 1. 系统边界

精灵系统由四个生命周期不同的对象组成：

| 对象 | 生命周期 | 责任 |
| --- | --- | --- |
| 精灵球 | 战斗卡牌 | 请求捕获检定并触发敌人离场结算 |
| `SpiritInstance` | 跨旅程永久档案 | 保存 UID、身份、成长、能力、归元和展示快照 |
| `SpiritAdventureParty` | 单次旅程 | 保存六个携带槽与唯一出战 UID |
| `SpiritOtherObj` | 单场战斗 | 作为原生 Partner 执行冻结后的精灵意图 |

同种精灵可以重复捕获。每个个体拥有独立 UID、元素、资质、速度、等级、成长计划和归元状态。

## 2. 捕获

目标必须存活、属于敌人、具有可用的 `Animation/Dict` 与 `Animation/Idle`。本地捕获还要求图鉴已经解锁；联机主机从权威敌人状态重新检查目标，但不读取远端玩家本地图鉴。

```text
成功率 = clamp(10% + 已损失生命百分比 × 0.8, 10%, 90%)
```

成功事务顺序：

1. 权威端完成捕获检定。
2. 创建独立 UID、固定资质和固定速度。
3. 解析稳定 `speciesId/profileId`、种族捕获元素与固有能力计划。
4. 原子写入永久档案。
5. 填充当前旅程和默认编队的首个空位。
6. 执行敌人死亡、后继阶段压制和离场兜底。

永久档案写入失败时不让敌人离场。档案使用 `.tmp` 写入、`.bak` 替换和损坏文件保留。

### 2.1 个体元素与逐段结算

元素绑定 `SpiritInstance` 个体，而不是只从种族临时计算。同种族的不同个体允许在后续系统中拥有不同元素；当前捕获流程仍按养成注册表的 `captureElement` 为该种族确定性赋值。低置信种族沿用当前表，后续体验调整只修改数据映射，不改变档案语义。

支持火、水、岩、草、风、雷、冰七种元素。精灵每段直接攻击都额外执行一次自身元素结算，多段攻击不得合并为一次附着：

- 火、水、雷、冰、草可以留下持续附着并参与后续反应；
- 风、岩可以触发现有反应，但命中后不单独留下持续附着；
- 元素伤害/反应由权威端逐段提交，客机只应用结果和表现。

元素信息以图标加文字显示在精灵列表格、编队槽、详情页标题、战斗名称栏、意图预览和捕捉结果。伤害意图采用 `雷 · 12×2` 一类格式，说明文字明确“每段进行雷元素结算”；不能只依赖颜色区分。

## 3. 永久档案与迁移

档案位置：

```text
AuraShared/Data/Owners/Terrias/SpiritCollectionProfiles/{owner}.json
```

version 10 保存：

- 永久个体、默认六槽编队和默认出战 UID；
- 个体 `ElementId`、赋值来源与映射 revision；
- 捕获与战斗经验幂等 token；
- 固定四语展示快照；
- `InherentAbilityPlanVersion`、已解析固有意图和固有被动；
- 五阶段成长计划、已学会/已装备能力与 loadout revision/hash；
- 归元值、星级来源和四本源分配。
- 初始全精灵发放版本，用于阻止同一玩家档案重复领取整批个体。
- 账号级圣遗物仓库、精粹、目标套装、抽取保底/回执和每只精灵的五槽配置。

旧档首次加载时统一规范化并立即写回。旧动态精灵卡仍只迁移一次，迁移完成后从冒险牌组移除。

### 3.1 初始全精灵发放

Terrias 使用游戏主体识别的 `Configuration.json` 暴露 `GrantAllSpiritsOnFirstLoad` 开关，发布默认值为 `true`，修改后需要重启游戏。
初始清单的领域 Profile 可使用去掉 `enemy_` 的稳定游戏主体 ID；提交前由
`EnemyCatalogApi` 按 `sourceModId` 解析为真实 `enemy_*` 或 owner-qualified 敌人 ID，
并对全部 58 项做完整预检。游戏数据目录尚未发布时，`SpiritCollectionApi` 持有明确的
pending 责任；新的 native catalog epoch 会在下一帧排空该责任。只有 58 项全部解析并
通过注册表依赖检查后才原子写入收藏与版本标记，失败不会留下半套初始精灵。

稳定玩家档案首次检测到开关启用且尚未完成当前发放版本时，以 `spirit.growth.registry.json` 的 58 个显式 `ProfileId` 为完整清单，直接新增每个 Profile 对应的精灵个体各一只。该事务不检查或补齐现有收藏；玩家已经拥有同 Profile 个体时仍会再获得一只。整批个体沿用普通捕获的等级、资质、速度、元素、固有能力和展示快照初始化，但不写捕获幂等 token，不修改默认六槽编队，也不修改当前旅程编队。

58 个个体与发放版本只执行一次原子写入。配置、注册表、敌人行或档案写入任一环节失败时不提交任何个体和完成标记；损坏且无法从备份恢复的档案禁止自动发放。配置为 `false` 时不写完成标记，后续改为 `true` 并重启仍会执行完整批次。

## 4. 成长与归元

等级上限为 50，累计经验为 4904。胜利时，开战快照中的出战精灵获得 100% 基础经验，其他携带精灵获得 25%，仓库与本场新捕获精灵不获得经验。

四大本源为魔力、精神、幸运、感知。物种成长来自 `spirit.growth.registry.json`，资质只影响成长部分，不改变 1 级基础值。战斗生命、攻击、护甲和魔能由本源统一换算。

归元只允许消耗相同 `speciesId`、未锁定且不在默认/当前编队中的个体。归元阈值为 `1/2/4/8/16`，对应一至五星；每星使最终生命、攻击和护甲提高 20%。四本源累计分配预算为 `0/2/6/12/20/30`，单轴最多 10 点。

## 5. 固有能力与外部兼容

当前养成注册表包含：

- 15 个通用意图；
- 12 个通用被动；
- 51 个种族固有被动和 58 套形态默认装配；
- 1 个外部兼容被动。

正式 profile 捕获时学会全部合法 PvE 固有意图，并冻结种族固有被动。每只精灵最多装备 3 个意图和 1 个被动。

未在 Terrias 注册表登记的外部 MOD 敌人不会读取或执行原始敌人脚本。系统按持久化的后备成长 profile 生成以下兼容套装：

1. 固定基础攻击；
2. 固定基础防御；
3. 按最高本源选择魔力、感知、精神或幸运分支；
4. 固定的“兼容核心”被动。

同一后备 `profileId` 使用同一固有兼容套装。若历史损坏或注册表异常导致有效装备为空，战斗解析器只注入基础攻击和基础防御作为最后保险，不回退到完整敌人意图池。

## 6. 种族被动

种族被动不再使用统一 `type-resonance` 占位模板。51 个稳定 ID 映射到 12 类可复用处理器，并通过阈值、收益、类型和上限形成 51 个不同机制签名：

- 回响节拍、蚀咒回流、护势循环、逆境驱动；
- 异式连携、蓄势待发、持盾共鸣、咒痕追猎；
- 护主契约、受击构型、魔能均衡、战意累进。

所有处理器由 `SpiritPassiveMechanicRegistry` 校验。伤害、护盾、治疗和 Buff 仍通过 `CompanionEffectCommitService` 提交；每个状态使用有界整数计数并进入战斗快照。

五阶段成长计划在捕获时确定。阶段 3 和阶段 5 选择通用被动时会检查当前能力是否可以触发该被动；阶段 4 会在前三个固定通用意图同型时确定性补入不同类型。

## 7. 编队与仓库

默认编队决定下一次旅程。进入旅程后复制为玩家私有旅程会话；旅程中的修改只影响后续战斗，不回写默认编队。联机各玩家分别保存自己的旅程会话。

仓库为三列固定尺寸虚拟化网格。列表只保留可见行和两行 overscan 的 12 至约 21 个复用单元；滚动只移动并重新绑定 RectTransform，不反复创建、销毁或重设父级。选择变化只刷新可见单元、详情和操作区。

## 8. 战斗出战与撤回

开战冻结六只携带、出战 UID、成长数值、归元、能力配置、注册表 hash 和 deployment token，并向本地玩家手牌加入一张 0 费 `Retain,Burnout` 出战卡。

同一拥有者同时只能有一只场上精灵。成功召唤后获得一张“换下”卡：

1. 换下保存生命、护盾、魔能、意图回合、冷却、被动计数和可见 Buff 状态；
2. 换下不触发死亡、奖励或捕获逻辑；
3. 返回的精灵卡费用增加 1；
4. 再次召唤恢复同一只精灵的完整战斗状态；
5. deployment token 仍限制为本场冻结的出战 UID，不能借此更换为编队中的其他精灵。

## 9. Partner、状态与 Hover

精灵使用原生 Partner 队列，但固定附着在拥有者右上角，不占横向友方槽。场上只常驻独立竖向生命/护盾条和意图图标，原生 `effectListObj` 始终隐藏。

Hover 时，视觉代理调用原生 `StatusManager.UpdateStatus(false)` 并打开原生 Tooltip：

- 单机和主机读取实际 `BuffDic`；
- 客机读取主机广播的只读 `VisibleStatuses`；
- 种族被动的进度、准备态和层数追加到 Tooltip；
- 客机不会通过展示快照调用 `AddBuff`，避免重复执行 Buff 行为。

## 10. 联机合同

Partner 协议当前为 22。主机执行意图规划、逐段元素结算、效果提交、被动与套装触发和状态推进；
客机只应用权威快照并播放表现。快照携带个体元素、registry hash、generation、revision、回合、
冷却、被动状态、最多五件圣遗物及最多 24 个只读可见状态。

本模块不把远端永久档案升级为防作弊权威。主机验证快照结构、公式、能力合法性和发送者角色归属，但远端收藏真实性仍属于受信客户端边界。

## 12. 圣遗物

账号级圣遗物仓库、精灵个体五槽、抽取/强化/分解事务、套装处理器、独立伤害乘区和 UI 以
[精灵圣遗物系统实现规格](../design/11-精灵圣遗物系统实现规格.md) 为准。圣遗物不是游戏原生 Relic 行，
不进入玩家全局遗物列表；其效果只作用于装备该配置的精灵战斗快照。
