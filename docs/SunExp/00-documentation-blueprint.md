# SunExp 技术文档蓝图

> 状态：规划基线，不是正式架构正文  
> 基线日期：2026-07-13  
> 反编译参考版本：`v1.0.23816797`

## 1. 目标

本轮文档从当前代码重新建立，不恢复、拼接或改写已删除的旧文档。最终文档需要让维护者能够回答：

1. SunExp 由哪些内容、代码、资源和运行时组成。
2. 每个功能从游戏数据入口到 C# 实现的完整调用链是什么。
3. SunExp 内容层、Aura 共享领域层、Aura 核心层和游戏主体之间如何分工。
4. 每个功能接入了游戏主体的哪个程序集、类型、方法、事件或 UI 生命周期。
5. 功能在单机、联机、异常初始化、版本签名漂移和资源缺失时如何处理。
6. 修改某个功能后应运行哪些构建、架构、内容或发布验证。

## 2. 统一分层口径

| 层级 | 本文档中的定义 | 当前主要位置 |
| --- | --- | --- |
| 内容交付层 | 游戏实际加载的 CSV、文本、资源、注册表和 DLL | `SunExp/` |
| SunExp 实现层 | SunExp 自有业务、适配、Hook、UI 和网络实现 | `SunExp-Dev/` |
| Aura 共享领域层 | Journey、CG、音频、皮肤、在线、UI 等可跨 MOD 复用的领域协议 | `Aura*Shared/`、各 Arbiter/Guard 项目 |
| Aura 核心层 | 不理解 SunExp 业务语义的注册、包、Hook、调度、配置和基础协议 | `AuraSharedCore/`，统一编译进 `Aura.Shared.dll` |
| 游戏主体或宿主层 | 官方游戏流程、数据模型、UI、脚本执行器和网络框架 | `Managed/` 与反编译目录中的 `Witch`、`Witch.Core`、`Mirror` 等 |

术语中不单独使用含义不明的“核心层”。出现该词时必须写明是“Aura 核心层”还是“游戏主体核心 API”。

## 3. 读者与阅读路线

- 新维护者：总览 -> 加载链 -> C# 分层 -> 功能模块 -> 术语表。
- 内容作者：内容数据 -> 脚本入口 -> 卡牌/Buff/遗物/事件模块 -> 验证。
- 运行时维护者：C# 分层 -> Hook 与生命周期 -> 共享层 -> 性能与兼容。
- 联机维护者：共享层 -> 网络/RPC -> 模式状态 -> 同步场景表。
- 排障者：接入映射表 -> 对应模块 -> 生命周期/回退 -> 验证命令。

## 4. 事实来源与证据等级

### 4.1 来源优先级

1. `SunExp/`、`SunExp-Dev/`：当前 SunExp 行为与所有权的主要事实来源。
2. Aura 共享源码、架构测试和发布门禁：共享契约与跨消费者约束。
3. `Managed/`：当前编译签名契约。
4. `开发参考资料/反编译文件夹v1.0.23816797/`：游戏内部流程和宿主行为参考。
5. `apocalyptic-journey-mod-tutorial/`：官方 MOD 接入范式的辅助证据。
6. 已删除旧文档：默认排除，不作为当前事实来源。

### 4.2 文档标记

- **代码确认**：当前源码、配置或测试可直接证明。
- **反编译确认**：已定位到反编译程序集、类型和具体方法。
- **签名确认**：已与 `Managed/` 当前程序集签名核对。
- **合理推断**：根据调用关系或命名推断，但尚无完整宿主证据。
- **设计约束**：由当前架构门禁或共享协议规定，不等同于官方游戏行为。

正式文档不得把“合理推断”写成既成事实。反编译实现与 `Managed/` 签名冲突时，以 `Managed/` 作为编译契约，并记录兼容分派。

## 6. 正式文档职责

| 文档 | 只负责回答的问题 |
| --- | --- |
| 整体架构与运行全景 | 系统由什么组成，主要控制流、数据流和依赖方向是什么 |
| MOD 内容数据与加载链 | 游戏如何发现、加载、解析和调用 SunExp 的内容与脚本 |
| C# 分层与依赖规则 | 类型为什么放在当前层，允许和禁止的依赖是什么 |
| Aura 共享层与核心层接入 | 哪些能力由共享层提供，注册、所有权、覆盖和兼容如何处理 |
| 游戏主体接入机制 | CSV、初始化、事件、Hook、UI、资源和 RPC 分别如何进入宿主流程 |
| 功能模块文档 | 某一业务能力如何从入口运行到清理，不重复解释全局分层 |
| 接入映射表 | 提供可搜索的 SunExp -> 宿主程序集/类型/方法映射，不写长篇概念说明 |
| 术语表 | 统一中文名、英文名、代码标识、所属层和易混淆边界 |

## 7. 模块文档固定模板

每篇功能模块必须使用相同骨架：

1. 模块定位与边界。
2. 用户可见行为与非目标。
3. 内容入口：Data/Text/JSON/资源清单。
4. 初始化入口与启用条件。
5. 主调用链，至少包含一条 Mermaid 时序图或流程图。
6. `Scripting -> GameApi -> Mechanics -> Hooks/Features/Network` 的职责分配。
7. 状态模型：作用域、权威写入者、保存位置和清理时机。
8. Aura 共享/核心依赖及 owner id。
9. 游戏主体接入表：程序集、类、方法/事件、接入方式、证据等级。
10. 单机与联机差异。
11. 兼容分派、失败隔离和确定性回退。
12. 性能热点、缓存、池化或帧调度。
13. 关键源码导航。
14. 验证方式与已知限制。

## 8. 宿主接入追踪方法

每条宿主映射按以下顺序核验：

```text
Data/JSON/Entry/Hook 入口
-> SunExp 公共入口或运行时
-> GameApi 适配点
-> 当前 Managed 类型/签名
-> 反编译程序集和类型
-> 反编译具体方法及其上下游调用
-> SunExp 的 before/after/事件/RPC/UI 接入时机
```

映射表至少记录：SunExp 模块、当前源码位置、接入机制、宿主程序集、宿主类型、宿主成员、反编译路径、签名核验状态、用途和风险。仅找到同名类型而未阅读方法体时，不标记“反编译确认”。

## 9. 撰写批次

1. **批次 A，架构基线**：README、整体架构、加载链、C# 分层、共享/核心、游戏主体接入机制。
2. **批次 B，基础战斗内容**：卡牌/Buff/遗物、战斗事件/场地/标签、乌娜、洛奈尔。
3. **批次 C，大型模式**：日耀回忆、无尽之海、无尽深渊、地图与奖励。
4. **批次 D，扩展玩法**：伙伴/使魔、百变、投影、心变、事件/对话/Boss。
5. **批次 E，运行时横切能力**：视觉/UI、音频/BGM/皮肤/CG、网络、性能/兼容、构建发布。
6. **批次 F，索引收口**：内容实体清单、宿主映射表、所有权矩阵、术语表和交叉链接。

每一批先提交覆盖状态和不确定点，再写正文；不确定宿主行为不得用文案掩盖。

## 10. 完成标准

- 覆盖 `SunExp/` 的全部 Data/Text 类别、注册表和共享资源清单。
- 覆盖 `SunExp-Dev/` 的全部架构层；每个生产 C# 文件至少归属一个模块或横切章节。
- 覆盖 `Aura.Shared.csproj` 当前编入的全部共享组件。
- 每个 Runtime Hook 字符串目标在宿主映射表中有记录或明确标为待核验。
- 每个 CSV C# 调用入口都能追到 `Scripting` 公共方法。
- 大型模式包含启动、准备、地图、战斗、奖励、结算、旧存档和联机路径。
- 网络章节区分共享进度、玩家私有状态和纯表现事件。
- 文档链接、源码路径、类型名和验证命令通过自动检查。
- 不引用已删除旧文档作为当前架构依据。

## 11. 后续维护规则

- 文档页头记录代码基线提交和反编译版本。
- 新增 Data 类型、公共脚本入口、Hook 目标、共享组件或 RPC 时，同步更新索引。
- 源码重命名后由路径检查发现失效链接。
- 共享层变化同时检查所有消费者和打包 DLL 一致性。
- 术语以稳定代码 id 为主键，中文显示名变化不改变技术身份。
