# Representative Task Evaluation

Use realistic requests with a clean evaluator context. Let the evaluator read
the project entry and relevant skills/source. Do not give it the expected
routing or proposed repair. Ask for a plan and evidence, with no production
mutations. These tasks are examples to vary, not fixed wording assertions.

## Task pool

1. Correct one Terrias card's displayed wording while preserving its effect.
2. Repair a CG resource selection that resolves differently after reopening.
3. Investigate a replay that sealed successfully but fails on its first frame.
4. Diagnose an external trainer checkpoint that fails after interrupted commit.
5. Add a local AuraTools setting that must export/import through presets.
6. Investigate a summoned Spirit whose own Buff fails only on a remote owner's
   battle while enemy damage still works.
7. Change a shared public interface consumed by both products.
8. Add an ordinary story event without changing Solar Memory.
9. Draw a new card-art series after a benchmark was already approved in the
   conversation.
10. Reorganize skill references without changing gameplay or shipped binaries.

## Assessment

Assess the resulting decisions, not repeated phrases or an exact list of skills:

- Did the evaluator find the real owner and current source contract?
- Did it distinguish current behavior, design intent and historical incidents?
- Did it preserve requested scope and existing authorization?
- Did it select enough validation without duplicate builds, hidden training
  runs or prototype checks?
- Did it require real runtime evidence where necessary?
- Did it preserve user-approved art/approval constraints?
- Could the referenced commands and files actually be resolved?

A failed case should lead to a narrow supported correction, not another broad
prohibition. Rerun the affected case after that correction. Record any remaining
uncertainty and the concrete evidence still needed.
