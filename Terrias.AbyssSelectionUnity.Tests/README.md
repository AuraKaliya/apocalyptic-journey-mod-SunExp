# Abyss selection rendering acceptance

Run `tools/Test-TerriasAbyssSelectionUnity.ps1 -UnityPath <Unity 6000.0.46f1/Editor/Unity.exe> -GameDataDirectory <installed game data directory>` from the repository root. Later runs can reuse the extracted frame fixture while its Witch.dll fingerprint still matches repository Managed.

The runner mirrors the current production contour rasterizer, sprite cache, source projection, selection component and UI rectangle helper. It copies both actual Abyss option artworks and verifies their hashes after the run. Generated mirrors, fixture copies and Unity caches are ignored.

The four PlayMode cases render with URP 17 and a real GPU. They cover selected/unselected artwork pixels, a native-style MeshRenderer frame with flipped UVs and perspective depth, transparent raycast targets, pointer exit, pooling reset, stencil clipping and unreadable texture cache reuse.

The Image regression uses the installed game's real card-frame texture. Its original Sprite metadata is retained for diagnosis; Unity repacks the texture into a tight atlas to exercise trimmed UVs and asymmetric Sprite padding. The test compares selection bounds with the mesh actually generated by Unity Image, including aspect fitting. This caught the former 384-wide selection over a roughly 281-wide rendered test sprite; the original shipped Sprite is 384 square with a roughly 219-by-338 texture rectangle. Repacking can produce different trim values, so the independent oracle is the actual rendered mesh, not a copied drawing formula.

The MeshRenderer case remains a synthetic geometry fixture. The suite does not load the complete DictionaryUI or claim in-game end-to-end acceptance.

Results and screenshots are written to `output/abyss-selection-unity`. No source bitmap, native material or game installation is modified.
