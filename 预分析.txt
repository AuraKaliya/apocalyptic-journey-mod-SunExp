结论很明确：当前【模拟战斗】不能完整复现【真实战斗】。它是一个独立实现、可批量运行的“战斗语义替身”，不是游戏真实战斗运行时的无头版本。

所以你的推论需要补充三个前提：

1. 模拟器必须生成与真实战斗相同的合法动作。
2. 执行动作后的状态转移必须一致。
3. 训练验收必须把这种错误设为硬失败。

当前这三点都曾出现缺口。

## 一、为什么模型仍然能够通过训练

这里其实存在两类不同问题。

### 1. 无意义结束回合：模拟里出现过，但旧验收没有拦截

旧底模自己的验证结果是：

- 主动结束回合：15,846 次
- 有剩余能量时结束：3,710 次
- 结束时浪费能量总量：9,734
- 严重结束回合错误：0
- 最终 `BehaviorPassed = true`

这些数据就在[阿米莉娅-全卡包底模.json](</AuraToolsExp/ModResource/Model/阿米莉娅-全卡包底模.json:78>)。

也就是说，不是“模拟中没有出现”，而是旧规则只把非常狭窄的一类结束回合判为 `SevereEndTurnMistake`。剩余能量结束回合只是统计项，不是硬性淘汰项。

因此模型完全可以：

> 在模拟里频繁浪费能量结束回合 → 胜率仍然达标 → 严重错误计数仍为 0 → 通过训练。

我们上一轮已经把当前版本改成：

```text
SevereEndTurnMistakes == 0
并且
AvoidableEndTurnsWithUnusedEnergy == 0
```

对应当前验收逻辑在[CombatCampaignFoundationTraining.cs](/AuraCombatAiShared/CombatCampaignFoundationTraining.cs:3018)。这修复了旧底模的主要准入漏洞，但只解决了“验收标准”这一层。

### 2. 【神选】无效循环：模拟器实际上掩盖了这个问题

这是目前最直接的模拟失真证据。

真实【神选】脚本的行为是：

- 抽牌堆为空：直接返回，不进入冷却。
- 手牌已满：直接返回，不进入冷却。
- 成功进入选牌并取牌后：才增加冷却。

规则集里保留了这段原始脚本，见[witch-base-evaluation-v2.ruleset.json](/AuraToolsExp/Config/combat-simulation/witch-base-evaluation-v2.ruleset.json:1276)。

但是模拟器有三个不同之处：

- 构造技能合法动作时，只检查技能冷却和 `Unusable` 标签，不检查抽牌堆、手牌上限等技能前置条件，见[CombatSimulationEngine.cs](/AuraCombatSimulationShared/CombatSimulationEngine.cs:1282)。
- 规则集甚至错误地把【神选】标记成 `requiresEnemyTarget: true`，见[witch-base-evaluation-v2.ruleset.json](D:/Project/Apocalypic-journey-mods-creator/ModExp/AuraToolsExp/Config/combat-simulation/witch-base-evaluation-v2.ruleset.json:1261)。
- 最关键的是，无论原生脚本是否提前返回，模拟器最后都会强制给技能设置至少一回合冷却，见[CombatSimulationEngine.cs](/AuraCombatSimulationShared/CombatSimulationEngine.cs:981)。

所以在抽牌堆为空时：

| 流程 | 结果 |
|---|---|
| 真实战斗 | 【神选】提示成功但无效果、不进冷却，可以再次选择 |
| 模拟战斗 | 脚本无效果，但模拟器随后强制进入冷却，无法连续选择 |

这恰好把真实战斗中最危险的重复无效动作掩盖掉了。

## 二、模拟和真实战斗到底共用了什么

它们共用的主要是：

- 状态特征结构
- 候选动作结构
- 模型评分与搜索逻辑
- 结束回合安全判断
- 部分卡牌、状态、敌人语义定义

但执行层完全不同。

真实战斗通过游戏里的 `FightUI`、卡牌对象和技能对象执行 `TrueUse()`，见[WitchCombatRuntime.cs](/AuraCombatAiShared/GameApi/WitchCombatRuntime.cs:351)。

模拟器则自己实现：

- 抽牌、弃牌、消耗
- 能量扣除
- 技能冷却
- 状态触发
- 敌人行动
- 回合切换
- 卡牌效果解释

见[CombatSimulationEngine.cs]/AuraCombatSimulationShared/CombatSimulationEngine.cs:352)。

因此它不能自然继承游戏主体里的这些行为：

- `TrueUse()` 的提前返回与提交时机
- UI 是否忙碌、是否真的可以行动
- 选择窗口打开、取消、超时、空选择
- 动画和协程结算顺序
- 游戏脚本中的隐藏副作用
- 实际目标绑定方式
- “调用成功”和“动作真正生效”的区别

例如模拟器中的选牌不是一个真实的决策阶段，而是直接取列表前 N 张：

[ AuraToolsNativeRewardSimulationRuntime.cs]/AuraToolsExp-Dev/Features/AutoBattle/AuraToolsNativeRewardSimulationRuntime.cs:2592)

这会系统性高估交互牌的稳定性。

## 三、`Authoritative` 目前也不能证明与实战一致

当前所谓 `Authoritative`，主要表示：

> 规则集中所引用的卡牌、状态、敌人具有“权威语义”标记。

模拟回放只要语义覆盖率达到 100%，就会被标记为权威样本，见[CombatEpisodeRecorder.cs](/AuraCombatAiShared/CombatEpisodeRecorder.cs:98)。

但是语义投影器、教师策略、模拟执行器都读取同一份规则集。它们证明的是“模拟系统内部是否自洽”，不是“模拟结果是否和真实游戏一致”。

此前训练摘要中甚至已经记录到大量选中动作的语义不一致，【神选】还是主要来源之一；但这些语义不一致只被统计，没有进入模型准入硬门槛。

所以目前的 `Authoritative` 更准确的名字应当是：

> `RulesetComplete` / 规则集覆盖完整

只有经过真实战斗差分验证的语义，才适合称为 `LiveVerified`。

## 四、科学的改进方向

不建议试图一次性把 Unity 游戏完整复制进模拟器。更可靠的方案是三层验证。

### 第一层：离线模拟训练

继续承担：

- 大规模自博弈
- 不同牌组和敌人的覆盖
- 搜索策略训练
- 能量、伤害、循环和生存价值学习
- 快速回归测试

但不再把“模拟通过”视为最终质量证明。

### 第二层：真实战斗差分测试

从真实战斗记录以下四部分：

```text
动作前真实状态
→ 执行的动作
→ 交互/目标选择轨迹
→ 结算后真实状态
```

然后在模拟器中重放相同状态与动作，比较：

- HP、护盾、能量
- 手牌、抽牌堆、弃牌堆、消耗堆
- 技能冷却
- 状态层数
- 敌人存活与限伤
- 是否打开选择窗口
- 动作是生效、无效、被拒绝还是等待选择

这样才能发现【神选】这种“脚本返回了，但模拟器仍然提交冷却”的差异。

### 第三层：真实游戏闭环验收

模型晋级前必须在真实游戏里跑固定场景，至少硬性检查：

- 可避免的剩余能量结束回合必须为 0
- 重复无效动作必须为 0
- 动作拒绝、超时和无状态变化必须低于阈值
- 核心职业技能的真实语义差分必须为 0
- 非循环初始牌组不能因能量惩罚提前结束
- 成型循环与普通剩余能量必须正确区分
- 敌人限伤已饱和时，允许合理结束回合

## 五、模拟器本身应如何改造

第一步不是只为【神选】写一个特殊判断，而是建立通用的动作结算协议：

```text
Rejected       不合法，未执行
NoEffect       已调用，但没有产生有效结果
AwaitingChoice 正在等待目标或选牌
Applied        动作真正提交并生效
```

然后让卡牌移动、能量扣除和技能冷却根据“提交点”决定，而不是只要进入 `ApplyPlayerAction()` 就默认成功。

规则定义还需要表达：

- `RequiresNonEmptyDrawPile`
- `RequiresHandCapacity`
- `MinimumSelectableCount`
- `TargetMode`
- `OpensSelection`
- `CooldownOnSuccessfulResolution`
- `CostOnSuccessfulResolution`

对于【神选】，模拟语义就应当是：

```text
抽牌堆为空 → 不提供动作，或返回 NoEffect 且不冷却
手牌已满   → 不提供动作，或返回 NoEffect 且不冷却
成功选牌   → Applied，取牌并进入冷却
取消选择   → NoEffect，不进入冷却
```

## 六、建议的实施优先级

P0，先解决会污染训练的核心差异：

- 修正【神选】的目标模式。
- 增加抽牌堆和手牌容量前置条件。
- 技能只在真实提交后进入冷却。
- 为“空抽牌堆、满手牌、正常选牌、取消选择”建立差分用例。
- 核心职业技能的“选中语义不一致”设为零容忍。

P1，建立通用机制：

- 显式动作结算结果。
- 显式交互选择状态。
- 真实战斗状态转移记录与模拟重放工具。
- 语义不一致进入训练准入门槛。

P2，再扩大覆盖：

- 卡牌、状态、遗物、祝福和敌人脚本的真实差分覆盖矩阵。
- 固定场景的真实战斗回归。
- 新模型先影子运行，再允许正式导入。

最终判断是：

> 当前模拟器足够用于“生成大量训练经验”，但还不足以单独证明模型能在真实战斗中正确工作。

上一轮对结束回合门槛和实战保护的修改是必要的；下一阶段最重要的不是继续调评分，而是建立“模拟状态转移 ↔ 真实状态转移”的差分验证体系。只有完成这一层，我们才能区分到底是模型学坏了，还是它学到的世界本身就和真实游戏不同。
