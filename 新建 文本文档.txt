结论：本轮训练系统本身运行稳定、并行效率正常，但训练结果确实不合格。失败不是“搜索预算仍然太小”，而是同时存在：

1. 一处可以确认的重生/逃脱终局判定错误；
2. 一个需要立即核查的玩家 BUFF 重复状态异常；
3. 高级与困难样本在“战役数量”上达标，但在实际训练轨迹中严重不足；
4. 困难种子重复训练没有形成有效恢复；
5. 模型晋升门槛过于僵硬，导致第 3 轮以后冠军基本冻结；
6. 构筑策略缺少“进入战斗前必死风险”的判断。

因此我不建议现在继续扩大网络或全局增加搜索预算。

## 一、确认存在重生终局判定错误

26个普通失败中，至少3个并非真正死亡：

- Seed `2000002`
- Seed `2000027`
- Seed `2000042`

这些战斗均记录为：

- 初始终局生命：0；
- 触发`blessing_35`【重生保险】；
- 最终玩家生命恢复到100；
- 但战斗结果仍是Defeat；
- 本轮全局`RuleTerminalOverrides=0`。

其中日志诊断清楚记录了：

```text
Heal:blessing_35:...:handler=blessing_35:Dead
```

但没有正确执行“复活后脱离战斗”的胜利覆盖。

当前模拟器已经有`Resurrection()`和`EscapeFight()`实现，[AuraToolsNativeRewardSimulationRuntime.cs](D:/Project/Apocalypic-journey-mods-creator/ModExp/AuraToolsExp-Dev/Features/AutoBattle/AuraToolsNativeRewardSimulationRuntime.cs:2350)，引擎也有物理死亡被规则胜利覆盖的机制，[CombatSimulationEngine.cs](D:/Project/Apocalypic-journey-mods-creator/ModExp/AuraCombatSimulationShared/CombatSimulationEngine.cs:879)。说明问题更可能发生在真实原生`Dead`回调的执行时机，而现有测试只覆盖了合成的`BattleEnded`晚期覆盖场景。

即使把这3场全部修正为成功，本轮也只是：

```text
25/48 = 52.1%
```

所以这是必须修复的问题，但不是通过率低的唯一原因。

## 二、发现严重的 BUFF 重复状态异常

我检查了最终验证的1,240场战斗状态，其中1,231场的玩家状态列表包含重复BUFF ID。

常见形式是：

```text
buff_elements:4
buff_extraordinary:78
buff_elements:4
buff_extraordinary:78
```

重复项的层数和来源完全相同，而且只集中在玩家身上。

目前还不能只凭报告断定是：

- 战斗状态真的重复添加了BUFF；还是
- 最终状态序列化/汇总时复制了两遍。

但无论是哪种情况都需要优先处理：

- 如果是真实状态重复，触发器、网络特征和搜索估值都可能被重复计算；
- 如果只是报告重复，成功案例分析和训练诊断也不可信；
- 当前`TerminalConsistencyViolations=0`说明完整性检查没有覆盖“同一角色同一BUFF重复实例”这一类问题。

建议新增状态不变量：每个角色的BUFF按ID唯一；若游戏语义允许多来源，则也应明确按`BUFF ID + 来源`归并，而不是出现完全相同的副本。

## 三、训练课程“按战役达标，按轨迹失衡”

后期每轮42个新战役中安排了13个高级战役，约31%，表面上满足高级保底。

但第8轮实际训练轨迹为：

```text
普通 2083
高级 317
总计 2400
```

高级轨迹实际只有13.2%。

原因是高级与困难战役死得早，生成的战斗轨迹少；普通成功战役能完整跑37战，自然贡献大量样本。结果就是：

> 按战役分配了高级训练，按真正进入神经网络的Episode计算，高级仍然严重不足。

报告中的大量`advanced:victory/defeat quota shortfall`正是这一问题的直接证据。[训练迭代](<D:/Steam/steamapps/common/Witch's Apocalyptic Journey/Witch's Apocalyptic Journey_Data/ModsData/AuraShared/Logs/AuraToolsExp/combat-simulation-results/20260726-235829-129-foundation/foundation-training-report.md:44>)

课程比例应从“战役数量配额”改成“最终训练样本配额”。

## 四、困难种子机制没有真正解决失败

第2～8轮每轮训练22个困难种子，共154次，成功恢复只有：

```text
0 + 0 + 3 + 1 + 1 + 2 + 0 = 7
恢复率约4.5%
```

反复失败的主要场景包括：

- `level_10011`：4次最终验证失败；
- `level_10010`：3次；
- `level_10029`：2次；
- `level_10045`：2次；
- `level_10040`：2次；
- 最终首领：4次。

问题在于当前困难训练仍然主要从战役开头重新跑。对于第5战、第11战或Boss失败来说，大部分计算都花在重复前置流程上，真正失败局面只得到一次短暂训练。

建议改成“失败前检查点局部训练”：

1. 保存失败战斗开始前的完整战役状态；
2. 直接从该战斗恢复；
3. 用教师搜索运行4～8个探索变体；
4. 找到成功解后，再回到完整战役验证；
5. 对失败决策附近的样本赋予2～3倍权重。

这会比简单把困难种子数量从22增加到44更有效。

## 五、冠军模型在第3轮后基本冻结

正式冠军只在第1轮和第3轮更新。第4～8轮全部拒绝。

例如第4轮：

- 冠军普通：53.1%
- 候选普通：59.4%
- 冠军高级：3.1%
- 候选高级：0%
- 候选独赢/冠军独赢：3/2

候选普通表现更好，但因为高级少输了一场，就在32对高级筛选样本上直接被否决。高级基准接近0时，一场比赛就是3.1个百分点，统计噪声非常大。

建议改成三类检查点：

- 普通能力最优；
- 高级能力最优；
- 综合正式冠军。

课程训练可以从“当前阶段最优检查点”继续，不必要求它立刻取代正式冠军。竞技场出现一项改善、另一项置信区间重叠时，应进入128场确认赛，而不是直接拒绝。

## 六、构筑策略缺少战前风险控制

26个失败的层级分布为：

| 失败位置 | 数量 |
|---|---:|
| 第1～5战 | 4 |
| 第6～10战 | 8 |
| 第11～20战 | 5 |
| 第21～30战 | 4 |
| 第31～36战 | 1 |
| 最终Boss | 4 |

17/26在第20战前失败，所以当前核心问题并不是终局无限或Boss搜索深度，而是早中期生存。

其中两个失败可以明确追溯到`CrowdFundingRelic_24`【红糖豆沙馅馄饨】：

- 回合开始先直接扣血；
- 玩家进入战斗时分别只有17和2生命；
- 在AI获得行动机会前直接死亡；
- 其中一个虽有【重生保险】，又被终局错误判负。

构筑与遗物选择应增加“下一战开始前不可避免伤害”评估：

```text
当前生命
- 战斗开始扣血
- 回合开始扣血
- 敌人先制效果
+ 可在行动前触发的复活/保护
```

若结果小于等于0，应优先替换危险遗物、选择生存奖励或判定复活逃生资源是否可用。

## 推荐的下一轮开发顺序

第一阶段：模拟完整性修复

- 修复【重生保险】的复活、脱离与终局覆盖。
- 检查并消除玩家BUFF重复状态。
- 新增BUFF唯一性和复活逃生完整性检查。
- 规则集/训练兼容哈希升级。
- 隔离本轮回放、成功案例和困难种子，修复后重新干净训练。

第二阶段：训练样本重构

- 高级比例按Episode而非Campaign计算，最低25%。
- 困难样本按失败前检查点局部训练。
- 失败前后关键决策加权。
- 限制完整普通成功战役贡献的重复简单样本。
- 保持成功示范15%～20%，但不能挤占高级失败和困难恢复样本。

第三阶段：模型晋升重构

- 普通、高级、综合三个模型检查点。
- 32场筛选、最多128场序贯确认。
- 置信区间重叠时不直接判回退。
- 困难种子恢复率、平均完成深度纳入模型选择。
- 最终90%/50%仅作为部署验收，不直接作为每轮训练晋升条件。

第四阶段：构筑生存评估

- 增加战前必死风险。
- 危险遗物与自伤卡的净生命评估。
- 第一层就建立临时防御/回复倾向，而不是等待后期才确定副体系。
- 对早期高频失败敌人建立专门的构筑与战斗回归集。

网络仍建议保持`128/96/64`，学习率、批大小和当前动态搜索暂时不改。等上述问题修复后再做一次基线训练；否则继续增加网络、Epoch或搜索预算，只会更快、更精确地学习错误或失衡的数据。
